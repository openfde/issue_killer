# 提出修复建议

仅接收 `analysis_verified`。只创建 `.fde-ai/issues/<issue号>/solution/solution.md` 和 `solution.json`，包含推荐与替代方案、关联 claim ID、受影响组件/文件、风险、预期行为，以及标记为 `not_run` 的用户/CI 验证建议。不得在 `.fde-ai/runs/` 创建新产物。

**修复选项（A/B/C）**：存在多条可行路线或修复无法立即确定时，替代方案必须按 A/B/C 编号，每项包含：改动点（`文件:函数`）、机制、优点、缺点与风险（影响面/回归面）、验证方法与判据、工作量、是否需要构建/刷机；推荐项明确标注“推荐”并说明理由。选项必须互斥、可直接选择，供开发人员在 issue 回复中决策。

**修复置信度（硬性）**：在 `solution.json` 写入 `fix_confidence` 对象：`score`（0–100，取 `root_cause` 与 `fix` 两项的较低值）、`root_cause`、`fix`、`level`（high/medium/low）、`rationale`、`unknowns`（逐条列出未证实环节）。锚点：90–100 为崩溃栈+完整日志链+源码路径闭合且单一最小修复；70–89 为主链闭合、1 个未证实环节不影响修复点；50–69 为根因基本成立但触发链有缺口或存在 ≥2 条互斥路线；<50 为根因或路线未证实。每个未证实环节或互斥路线按实际影响扣分，不得无依据给高分。该分数供编排器分流（≥70 生成修复 PR；50–69 生成分析回复；<50 深度分析），不得在产物中声称已验证。

**调试日志策略（按需）**：当修复把握不足、行为存在不确定性或预计需要设备侧调试时，方案应包含针对性日志（沿用模块既有 TAG 体系）；级别遵循——状态迁移/关键分支 `d`/`i`，被拒绝或异常路径 `w`，错误 `e`；频率仅在用户操作与状态变化点记录，**禁止逐帧/循环内高频打印**（确需高频时用 DEBUG 守卫或限频）；日志包含判定依据与关键值（输入参数、阈值、计算结果），不得包含凭据或个人数据。**高置信度的最小修复不需要额外日志**，保持补丁精简。

推进到 `solution_proposed`。建议无法关联已验证 claim 时停止。不得编辑工作副本、声称已修复或运行验证命令。
