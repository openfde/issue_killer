# 起草原因链与修复选项回复

仅接收 `analysis_verified`（原因链）与 `solution_proposed`（修复选项）。只写 `.fde-ai/issues/<issue号>/comment/analysis-options.md`。不得调用 GitHub；不得自动发布。必须在会话中展示草案要点并等待用户选择 A/B/C：A=发布、B=修改、C=暂停。只有用户选择 A 后，才由编排写入 `publication/approval.json` 并调用 `publish-policy-comment`。

适用：**无法立即修复**的问题——根因存在未证实环节、需要复现实验、存在多条互相权衡的修复路线、或改动影响面需要开发决策。不要用于根因明确且修复单一的问题（直接走 patch/PR 流程）。

回复结构（专业、纯技术）：

1. **结论**：一句话说明失效机制与关键触发条件；随后写明“修复置信度：<score>%（根因 <root_cause>% / 修复 <fix>%，依据……）”，标注证据等级与置信度。
2. **问题原因链**（主体，按时间与调用顺序）：
   - 触发条件与前置状态；
   - 关键时间线（毫秒级日志、进程/线程、关键状态值）；
   - 完整因果链：每一步给出 `文件:行号`、证据 ID/日志时间戳与状态迁移；区分直接原因、根本原因、放大因素；
   - 现有容错/兜底路径为何失效：逐条说明被哪个同一故障击穿；
   - 未证实环节：明确标注“推断，未证实”，并给出可判定的验证实验；
   - 影响面与已排除项（含排除依据）。
3. **修复选项 A/B/C**（来自 solution 的推荐与替代，逐项编号）：
   - 50–69 时作为主要选项；<50 时标注“低置信候选，未证实”；
   - 改动点（`文件:函数`）、机制、优点、缺点与风险（影响面/回归面）、验证方法与判据、是否需要构建/刷机；
   - 推荐项标注“推荐”并说明理由；选项必须互斥、可直接选择。
4. **可选证据补强（只列选项，不展开）**：
   - **D. 复现与验证方案**：稳定复现、观测点、修复后判据、根因确认实验；选中后由分析助手展开并追加一条 issue 回复；
   - **E. 调试 PR（插桩）**：只加日志/埋点、不改行为、需人工构建刷机；选中后创建 `ai-debug/` 分支 PR；
   - **F. 深入分析**：分析助手继续排查（仅在修复置信度 <50 或开发要求时提供）。
5. **请求决策**：请开发人员回复 A/B/C/D/E/F（可附补充约束）；A/B/C 将据此生成补丁/PR，D/E 由分析助手展开或创建，F 继续深度分析。
6. 落款 `*由 AI 修复助手生成、未验证；内容仅供参考，不代表已验证结论。*`，文末 marker `<!-- openfde-ai:analysis-options issue=<编号> revision=<版本> -->`。

写作规范（硬性）：

- 纯技术分析：禁止“值得注意的是/综上所述/总的来说/希望对你有帮助”等套话、情绪化形容词与空泛总结；直接陈述事实、机制与依据。
- 每个结论必须有依据（证据 ID、日志时间戳、`文件:行号`）；无依据的推断必须标注“推断，未证实”。
- 术语保持原样（如 EGL surface、gralloc、BufferQueue），不要口语化替换。
- 不得写出 `.fde-ai/`、`data/` 等内部产物路径，不得出现“分析产物”字样；不粘贴原始附件与凭据。
- 长度以“开发可直接判断”为准：原因链完整，不重复同一证据。

推进到 `analysis_options_drafted`。
