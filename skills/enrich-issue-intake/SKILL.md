# 整理最简 issue 为标准取证格式

触发：轮询发现新提交的最简 issue（正文很短、含附件、无 `openfde-ai:intake` marker），或调用方显式指定编号。**只改写该 issue 的标题与正文**（`gh issue edit`），不得关闭/合并/删除，不得改动评论与附件本身。

步骤：

1. 读取 issue（`gh api repos/<repo>/issues/<n>`）：标题、正文、附件链接（`user-attachments`）、创建时间、作者。**作者不是当前 `gh` 登录用户时跳过**（记录原因）。
2. 定位 bugreport：附件中的 `.zip`（文件名含 `bugreport`）或正文/调用方给出的 VM 本地路径；从文件名与内容解析**版本号**与**抓取时间**；发生时间只能精确到**范围**（调用方给“约 HH:MM–HH:MM”即可，未知则写“待补充”）。
3. 生成标准正文（**保留原始描述**）：

   - 首行隐藏 marker：`<!-- openfde-ai:intake issue=<n> -->`（幂等，已存在则跳过）；
   - `## 现象`：一句话 + 偶现频率（原文有则引用）；
   - `## 时间线（事后补抓）`：发生时间范围、抓取时间（取自 bugreport 文件名）、期间是否重启（未知写“待补充”）；
   - `## 环境`：设备/版本（`fde_arm64-<版本>` 或 `version.txt`）；
   - `## 复现步骤（推测，未确认）`：把原文操作整理为步骤，明确标注“偶现、未现场复现，以下为事后推测”；
   - `## 预期结果` / `## 实际结果`；
   - `## 附件`：只列文件名与用途（**不写 SHA-256**）；
   - `## 下次偶现采集建议`：PC 常驻 `adb logcat -b all -v threadtime > logcat_$(date +%H%M).txt`（出现后立即停止并连同截图/bugreport 附上）；不要重启设备；记录发生时间范围；
   - `## 备注`：事后补抓、未现场复现；由 AI 取证助手整理，未验证；
   - `> 原始描述：<原文>`（完整保留，避免信息丢失）。

4. 标题整理为 `<现象摘要>（<版本号>）`（版本号缺失时保留原标题）。
5. 大小处理：附件 >24MB 时**不重复上传**；若正文提及 VM 可访问的本地路径，生成“发生时间范围 ±30 分钟主日志 + crash buffer + dropbox 摘要”的时间窗摘录包（≤24MB）并在正文说明需人工补充附件；否则提示人工分卷。
6. 写回：`gh issue edit <n> --repo <repo> --title <新标题> --body-file <新正文>`；记录 `data/intake/<日期>-<slug>/enrichment.json`（marker、原/新正文哈希、附件清单、时间戳）；把整理后的证据登记到 `input/` 不得触碰附件文件本身。
7. 汇报：issue 链接、时间线（范围）、附件、待补充项（发生时间/重启等）。

边界：不得改动源码/缓存；不得发布评论（除非提示附件过大，按 `interaction_comments` 策略）；不得编辑非新建或他人 issue；marker 已存在时跳过；不得在 `.fde-ai/runs/` 创建产物。
