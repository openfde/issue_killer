# 整理最简 issue 为标准取证格式（手动触发）

**仅由调用方显式指定 issue 编号时使用**；不得批量扫描、不得自动选择新 issue。只改写该 issue 的标题与正文（`gh issue edit`），不得关闭/合并/删除，不得改动评论与附件本身。

步骤：

1. 读取 issue（`gh api repos/<repo>/issues/<n>`）：标题、正文、附件链接（`user-attachments`）、创建时间、作者。
2. **证据判定**：
   - **有 bugreport 附件**（`.zip`，文件名含 `bugreport`，或正文/调用方给出 VM 本地路径）：解析版本号与抓取时间；发生时间只写**范围**（“约 HH:MM–HH:MM”，未知写“待补充”）。
   - **没有 bugreport（仅文字 + 截图）**：把图片附件下载到 `data/intake/<日期>-<slug>/input/`，**使用模型自身视觉直接读图**（不得引入 OCR 工具）；只提取图片中可见的技术事实（报错文本、界面状态、版本/设备信息），标注图片 SHA-256 与来源；证据等级记为 `description+screenshot`，并明确“**无日志证据**”。
3. 生成标准正文（完整保留原始描述）：

   - 首行隐藏 marker：`<!-- openfde-ai:intake issue=<n> -->`（已存在则跳过整理）；
   - `## 现象`：一句话 + 偶现频率（原文有则引用）；
   - `## 时间线`：发生时间范围、抓取时间（有 bugreport 时取自文件名）、期间是否重启（未知写“待补充”）；
   - `## 环境`：设备/版本（bugreport 文件名中的 `fde_arm64-<版本>`、`version.txt`，或截图中的可见版本；缺失写“待补充”）；
   - `## 复现步骤（推测，未确认）`：把原文操作整理为步骤，明确标注“偶现、未现场复现，以下为事后推测”；
   - `## 预期结果` / `## 实际结果`；
   - `## 附件`：只列文件名与用途（**不写 SHA-256**）；
   - **仅在没有 bugreport 时**增加 `## 初步分析（未验证）`：基于文字与截图解读现象；结合 `profiles/openfde/component-map/` 知识给出 1~3 个可疑组件/方向（标注“推测”，可选做一次受限 `rg` 检索，遵守检索纪律）；列出**建议补充的证据**（如 bugreport、对应子系统日志、复现时间范围），并注明“无日志证据，结论未经设备验证”；
   - `## 下次偶现采集建议`：PC 常驻 `adb logcat -b all -v threadtime > logcat_$(date +%H%M).txt`（出现后立即停止并连同截图/bugreport 附上）；不要重启设备；记录发生时间范围；
   - `## 备注`：事后补抓/未现场复现（有 bugreport 时）、由 AI 取证助手整理、未验证；
   - `> 原始描述：<原文>`（完整保留，避免信息丢失）。

4. 标题整理为 `<现象摘要>（<版本号>）`；版本号缺失时保留原标题，并在环境段写“版本待补充”。
5. 大小处理：bugreport >24MB 时**不重复上传**；若正文提及 VM 可访问的本地路径，生成“发生时间范围 ±30 分钟主日志 + crash buffer + dropbox 摘要”的时间窗摘录包（≤24MB），在正文说明需人工补充附件；否则提示人工分卷。
6. 写回：`gh issue edit <n> --repo <repo> --title <新标题> --body-file <新正文>`；在 `data/intake/<日期>-<slug>/enrichment.json` 记录 marker、原/新正文哈希、附件与图片清单、证据等级、时间戳。
7. 汇报：issue 链接、证据等级（`logs` 或 `description+screenshot`）、时间线（范围）、附件/截图、**初步分析要点（若有）**、待补充项。

边界：不得改动源码/缓存；不得发布评论或关闭 issue；不得编辑非指定编号；marker 已存在时跳过；不得在 `.fde-ai/runs/` 创建产物。
