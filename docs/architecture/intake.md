# 取证采集（提 issue 前）

取证助手是提 issue 前的交互式人工辅助：**发现问题和决定提 issue 始终由人完成**，助手把"抓什么、怎么抓"变成几步对话，不做长篇规划。大多数问题只需要 **bugreport + 截屏**。

## 交互流程

1. 人工给出一句话现象（可选设备型号/版本、复现时刻）；
2. 助手简短评估并给出采集集请确认：默认 `bugreport` + 现象截图；录屏可选（复现/闪烁/动画类建议加）；仅当现象明确属于某子系统时追加单条额外项（蓝牙 HCI snoop、显示/音频/网络 dumpsys 头部、tombstone 摘要）；
3. **确认门（硬性）**：助手停住等待——列出目标设备序列号、将执行的命令与开始时机；现场复现时收到“复现完成”后才开抓；未确认前不得执行任何采集命令（`adb devices` 枚举除外）；
4. 设备连接保持现状：服务器 `adb connect <IP>:5555` → 列 `adb devices` → 人工确认序列号（多设备显式 `-s`，不得自动挑选）；
5. 只读采集：`adb bugreport`、`adb exec-out screencap`、可选 `adb shell screenrecord` + `adb pull`；全程禁止 root、禁止 `logcat -c`、禁止安装/卸载/改设置；
6. 打包：`data/intake/<日期>-<slug>/` 内生成 zip（含简短 `summary.md`：现象、设备、时间、用途、SHA-256），总大小 ≤24MB（GitHub 附件上限 25MB），超限时把大文本成员 gzip 后重打包并说明；
7. 生成 issue 草稿：写 `issue-draft.md`——标题为 `<现象摘要>（<系统版本号>）`，正文含环境/复现/预期与实际/附件清单（文件名与用途；**哈希只保留在本地 `summary.md`，不写入 issue**；内网地址不写入）；最终输出附带**本机 scp 拉取附件命令**（服务器绝对路径），人工马上下载后新建 issue——粘贴草稿、拖入 zip+截图；助手不代提、不发布。

## 降级

服务器连不上设备时，助手直接在对话里给出 PC 端命令（`adb bugreport`、`adb exec-out screencap`、`adb pull`）由测试人员执行，不生成脚本文件。

## 最简 issue + 自动整理（推荐给测试人员）

测试人员不必先跑取证助手，直接提交一句话（+ bugreport 附件）即可：

1. issue 正文尽量短，附上 bugreport（GitHub 附件 ≤25MB；超限时在正文写 VM 上的文件路径，助手生成时间窗摘录包后由人工补充）；
2. 轮询每 3 分钟扫描新提交的最简 issue（短正文 + 附件链接、无 `openfde-ai:intake` marker、无 `no-ai-reply` 标签），自动调用 `enrich-issue-intake`：
   - 标题整理为 `<现象摘要>（<版本号>）`；
   - 正文整理为 现象 / **时间线（事后补抓，发生时间只写范围）** / 环境 / **复现步骤（推测，未确认）** / 预期与实际 / 附件（不写 SHA-256）/ **下次偶现采集建议** / 备注，并完整保留原始描述；
3. 助手只编辑该 issue（`gh issue edit`），不关闭、不发评论、不改附件；`publication.issue_enrichment=manual` 可关闭自动整理。

## 偶现 / 事后取证（D 模式）

已抓到 bugreport 但无法现场复现时，可在取证助手里选 **D. 事后证据**：

- 发生时间只给**范围**（未知写“待补充”），另有抓取时间与“是否重启”；
- 默认**不连接设备**、不执行任何设备命令，只校验并打包已有文件；
- bugreport 超 24MB 时生成时间窗摘录包（发生范围 ±30 分钟主日志 + crash buffer + dropbox 摘要）；
- 草稿同样标注“推测复现步骤（未确认）”，并附“下次偶现采集建议”（常驻 logcat、立即截图、不重启设备）。

## 与 issue 分析衔接

取证包作为 issue 首版证据附件；分析阶段直接读取附件（截图由模型视觉识别）。组件映射与子系统经验沉淀在 `component-map` 知识库中，与取证互不耦合。
