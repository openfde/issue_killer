# AI Issue 工作流讨论（1 页版）

## 简介

本工作流让 AI 从真实 bug 的设备日志采集开始，完成分析、修复 PR、编译安装和人工验证。当前已用 496、497、498 三个真实问题验证主链路；验证助手尚未实现，PR 合并和 issue 关闭仍由人工完成。本次讨论聚焦流程边界、人工控制、验证标准和构建环境。

## 当前流程

| 阶段 | 内容 | 人的参与 |
| --- | --- | --- |
| L0 采集 | `collect-device-evidence`：A/B/C/D、log.tag 预检、bugreport/截图/logcat、issue 草稿 | 选采集方式、确认设备、建 issue |
| L1 分析 | 证据提取、组件归属、源码追溯、置信度分流（50/70） | 关键节点选择 A/B/C/D/E/F |
| L2 修复 | patch、PR、交付评论；只创建不合入 | 确认修复路线、创建 PR |
| L3 构建安装 | issue 最新 PR、多模块/分支、`systemimage`、安装到 FDE | 选择构建范围、人工验证 |
| 收口 | 归档、知识候选；PR/issue 人工处理 | 验证、合并、关闭 |

## 待讨论/决策

1. **L3 验证标准**：模块构建能否算修复验证？产品配置改动是否必须 `systemimage` + A/B？是否要求刷机/OTA/回归？
2. **验证助手**：证据最低标准、谁确认“验证通过”、是否要独立账号/设备；验证评论删除后归档是否自动重开。
3. **发布控制**：分析选项/复现/调试评论是否保持全 manual？修复交付评论是否允许自动发布？`approval.json` 是否统一硬门槛？
4. **状态控制**：“继续 <编号>”只读、明确“继续分析/推进”才执行是否足够；归档后新证据如何重开 revision。
5. **构建/安装环境**：29/247 的 SSH/sudo 维护责任；容器只读导致的 module-map/install workaround 是否固化；`system.img` 接近上限的加包策略。

## 风险

- 498 的 PR #43 仍 open；产品配置只做 A/B 构建，未刷机/OTA 验证。
- 498 归档为 `fixed_verified_scope_limited`；验证评论曾删除，状态依据来自会话+快照。
- 模块构建和产品镜像验证容易混淆；`--no-pr` 必须显式记录。
- 采集依赖 adb，FDE adb 25555 曾离线；现场采集可能需 D 模式。
- 工作流是 AI 编排 + `state.json`，不是强一致状态机，模型可能偏离技能。
- `system.img` 接近分区上限，后续新增模块空间风险高。

## 建议议程（60 分钟）

1. 5 分钟：目标与当前状态
2. 15 分钟：L0–L3 流程与人工决策点
3. 15 分钟：验证助手、发布控制、状态重开
4. 10 分钟：构建/安装环境与 module-map 固化
5. 10 分钟：风险、负责人、下一步
6. 5 分钟：结论与行动项

## 建议结论（待会议确认）

- 产品配置类修复以 `systemimage + A/B` 为最低验证，不以模块构建代替。
- 分析/复现/调试评论保持 manual，必须有可追溯的人工批准。
- “继续 <编号>”只读；分析、发布、构建都需要明确指令。
- 先定义验证助手的证据标准，再决定是否自动化。
- module-map、安装脚本、构建/安装凭证维护责任明确到人。
